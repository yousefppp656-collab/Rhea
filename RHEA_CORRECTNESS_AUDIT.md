### 1.2 Actual Subsystem Entry Points & Execution Paths
All authoritative compiler and runtime execution paths reside in `native/cpp/src/rhea_driver.cpp` (`7,315` lines of C++20) and `native/cpp/src/kernels.cpp` (`635` lines of C++20):

| Compiler / Runtime Phase | Authoritative Class / Entry Point | Location in `rhea_driver.cpp` | Ownership & Execution Model |
|---|---|---|---|
| **1. Lexing** | `Lexer::tokenize()` | Lines `254`–`692` | Scans UTF-8 source into `std::vector<Token>` with 1-based `(line, col, length)` spans, duration literals (`ms`, `s`), and 64-bit integer overflow checks (`E1002`). |
| **2. Parsing** | `Parser::parse_program()`, `parse_stmt()`, `parse_expr()` | Lines `878`–`1895` | Recursive-descent + operator-precedence parser producing `Program` AST (`std::shared_ptr<Stmt>`, `std::shared_ptr<Expr>`), enforcing `MAX_PARSE_DEPTH = 256` and `MAX_TYPE_DEPTH = 32`. |
| **3. ## 2. Ranked List of Confirmed Defects & Fixes Applied in `v0.11.0`

| Defect ID | Severity | Subsystem(s) | Defect Description & Reproduction | Root-Cause Fix Applied & Regression Test |
|---|---|---|---|---|
| **D-01** | **HIGH** | `NativeCodegen` (`rhea compile`) | `NativeCodegen` emitted raw C++ `+`, `-`, `*`, `/`, `%`, unary `-`, and compound `+=`/`-=`/`*=`/`/=` without overflow or division-by-zero guards. Signed 64-bit overflow (`INT64_MAX + 1`, `INT64_MIN / -1`, `-INT64_MIN`) caused C++ UB instead of `E1002`, and `10.0 / 0.0` produced `inf` instead of `E1001`. | Emitted overloaded C++20 helpers `rhea_add`, `rhea_sub`, `rhea_mul`, `rhea_div`, `rhea_mod`, and `rhea_neg` with `__builtin_*_overflow` (`E1002`) and zero-divisor checks (`E1001`), lowering all binary, unary, and compound arithmetic through them (`test_96`, `test_97`, Differential Suites `15`, `16`). |
| **D-02** | **HIGH** | `BytecodeVM`, `NativeCodegen`, `Interpreter` | Top-level `const` bindings (`const LIMIT = 40`) were wiped by `locals.clear()` when `BytecodeVM` invoked `main()` (evaluating to `Unit`/`0`) and were emitted inside C++ `int main()` instead of file scope in `NativeCodegen` (failing C++ compilation when referenced inside functions or closures). | Added `__snapshot_globals` in `BytecodeCompiler`/`BytecodeVM` so `invoke_vm_fn` initializes `locals = globals;`, preserved `saved_scopes.front()` in `Interpreter::invoke_closure`, and emitted `Stmt::Kind::Const` at C++ file scope before functions in `NativeCodegen` (`test_98`, Differential Suite `17`). |
| **D-03** | **HIGH** | `Interpreter`, `BytecodeVM`, `TypeChecker` | Ordering comparisons (`<`, `<=`, `>`, `>=`) on `String` read `float_val` (`0.0`) in both `Interpreter` and `BytecodeVM`, causing `"apple" < "banana"` to evaluate to `false` (diverging from `NativeCodegen`). Additionally, `TypeChecker` permitted `<, <=, >, >=` on non-orderable types (`Bool`, `List`, `Map`, `Struct`). | Added lexicographical `String` comparison branches to `Interpreter::apply_binary` and `BytecodeVM` (`OpCode::Lt/Le/Gt/Ge`), and restricted `<, <=, >, >=` in `TypeChecker` to `Int`, `Float`, and `String` (`E0003` on non-orderable types, `test_99`, Differential Suite `18`). |
| **D-04** | **HIGH** | `TypeChecker`, `Interpreter`, `BytecodeCompiler`, `NativeCodegen` | Struct field assignment (`p.x = v`, `p.x += v`) fell through to `else { check_expr(st->target); }` in `TypeChecker`, bypassing mutability checks (`E0005`), field type checks (`E0003`), and shadow variable resolution (`resolved_name`). Compound assignments (`+=`, `-=`, `*=`, `/=`) on struct fields and list/map indices were also unimplemented in `Interpreter` and `BytecodeCompiler`. | Added explicit `Expr::Kind::FieldAccess` target validation in `TypeChecker::check_stmt` (`E0004`, `E0005`, `E0003`, `resolved_name`) and implemented compound `Index` and `FieldAccess` assignment across `Interpreter`, `BytecodeCompiler`, and `NativeCodegen` (`test_100`, Differential Suites `19`, `21`). |
| **D-05** | **HIGH** | `TypeChecker` | Modulo operator `%` was accepted on `Float` (`3.5 % 1.2`), causing a spurious runtime `E1001` in `rhea run`/`rhea vm` and a C++ compile error in `rhea compile`. | Restricted `%` to `Int` operands in `TypeChecker::check_expr` and generic body operator checking (`E0003`, `test_101`). |
| **D-06** | **HIGH** | `NativeCodegen` (`rhea compile`) | User-defined `struct` types had no generated `operator==`, `operator!=`, or `rhea_to_str` in `NativeCodegen`, causing `print(s)`, `str(s)`, and `s1 == s2` to fail C++ compilation; out-of-order field initializers (`Vec2 { y: 20, x: 10 }`) failed C++20 designated-initializer ordering rules. | Generated `operator==`, `operator!=`, and sorted-field `rhea_to_str` for all concrete and generic structs in `NativeCodegen`, and reordered struct initializer fields to declaration order during C++ emission (`test_102`, Differential Suite `19`). |
| **D-07** | **HIGH** | `TypeChecker`, `BytecodeCompiler`, `BytecodeVM`, `NativeCodegen` | In-place collection mutators `push(xs, v)`, `pop(xs)`, and `remove_key(m, k)` did not check that the target collection variable was `mut` (`E0005`) or validate `push` element types against `List<T>` (`E0003`), and `pop(xs)` was missing in `BytecodeVM` and `NativeCodegen`. | Enforced target mutability (`E0005`) and element types (`E0003`) in `TypeChecker`, and implemented `pop(xs)` (`__pop_val` in `BytecodeVM` and `rhea_fn_pop` in `NativeCodegen` with empty-list `E1003` trap, `test_103`, Differential Suite `21`). |
| **D-08** | **MEDIUM** | `TypeChecker` | Multi-parameter generics (`struct Entry<K, V>`, `fn lookup_or<K, V>(m: Map<K, V>, ...)`) failed unification/substitution because `unify_type_pattern` and `substitute_type_params` did not split comma-separated type arguments inside `<...>`. | **D-09** | **MEDIUM** | `CLI Driver`, `BytecodeCompiler` | When `fn main() -> Int` returned a non-zero integer (e.g. `return 7`), `rhea compile` exited with status `7`, whereas `rhea run` and `rhea vm` discarded `main`'s return value and exited with `0`. | Removed `OpCode::Pop` after `CallFn "main"` in `BytecodeCompiler` and propagated `main()`'s integer return value as the process exit code in `rhea run` and `rhea vm` (`test_105`, Differential Suite `23`). |
| **D-10** | **MEDIUM** | `Parser`, `TypeChecker` | `Parser` lacked a recursion depth guard (`MAX_PARSE_DEPTH = 256`) on nested expressions and blocks; `TypeChecker` did not reject duplicate struct fields, duplicate struct initializer fields, duplicate function/closure parameters, or cross-module duplicate public function names. | Added `parse_depth_` guard (`MAX_PARSE_DEPTH = 256` -> `E0002`) in `Parser::parse_expr` and `Parser::parse_block`, and added duplicate symbol checks (`E0002`) across struct fields, struct initializers, function/closure parameters, and imported modules (`test_106`, `test_107`, `test_119`). |
| **D-11** | **MEDIUM** | `NativeCodegen` | Empty typed list literals (`let mut names: List<String> = []`) defaulted to `std::vector<int64_t>{}` in `NativeCodegen`, and `rhea_range_excl` / `rhea_range_incl` lacked `__builtin_sub_overflow` and `MAX_RANGE_ELEMENTS` (`E1004`) checks. | Used `e->inferred_type` for `ListLit` element type mapping in `NativeCodegen` and added overflow + `10,000,000` element bounds checks (`E1004`) to `rhea_range_excl` / `rhea_range_incl` (`test_108`). |
| **D-12** | **MEDIUM** | `BytecodeVM`, `NativeCodegen` | `BytecodeVM` lacked a pre-execution bytecode verifier for constant indices, jump targets, and function targets; `NativeCodegen` lacked C++ runtime bindings for `std::string.*`, `std::io.is_eof`/`parse_int`/`parse_float`, and `std::log.*`. | Added `BytecodeVM::verify_chunk()` (`E2001`) before execution and added C++20 runtime helpers for `std::string.*`, `std::io.*`, and `std::log.*` in `NativeCodegen` (`test_109`). |

## 3. Remaining Architectural Risks & Known Limitations

1. **Nested Collection Mutation in `BytecodeVM` (`m["k"][0] = v` or `s.items[0] = v`)**:
   - Single-level index mutation (`xs[i] = v`, `m[k] = v`) and single-level struct field mutation (`s.field = v`, `s.field += v`) work identically across `rhea run`, `rhea vm`, and `rhea compile`. Chained multi-level lvalue mutation (`matrix[i][j] = v` or `s.items[i] = v`) is not yet supported in `Interpreter` or `BytecodeVM` because `Value` containers store value copies rather than reference cells.
2. **Closure Capture Semantics (Value Snapshot vs. Mutable Reference Sharing)**:
   - Closures intentionally capture enclosing variables by **lexical value snapshot** at closure creation time (`[=]` in C++20, value map copy in `Interpreter` and `BytecodeVM`). Mutating a captured variable inside a closure body is not supported.
3. **`std::ai.*` and `std::json.parse` in `NativeCodegen` (`rhea compile`)**:
   - `std::ai.*` tensor/autodiff operations and dynamic untyped `std::json.parse` are supported in `rhea run` (and `std::json` in `rhea vm`). Because `NativeCodegen` lowers Rhea types to static C++20 types (`int64_t`, `double`, `std::string`, `std::vector<T>`, `std::map<K, V>`) without a boxed `rhea::Value` variant in generated standalone binaries, dynamic heterogeneously-typed JSON DOM trees and `std::ai.tensor` calls remain Interpreter/VM capabilities unless linked against `librhea_native.so`.
4. **External Tooling Blockers (`rustc`/`cargo` and `vsce`)**:
   - The 13-crate Rust workspace (`crates/rhea_*`) and the VS Code extension source (`tools/vscode-rhea/`) are present on disk, but `rustc`/`cargo` and `vsce` are not installed on this host machine and remain reported as **`Blocked by environment`**.
